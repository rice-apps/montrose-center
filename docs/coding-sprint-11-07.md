Keep Supabase credentials in the backend. Use fictional service and contact data during development, and leave referrals in staff's existing channels.

## Shared contract and ownership

The catalog shape follows [the October 31 sprint](coding-sprint-10-31.md): a `services` row has `service_id`, `name`, `description`, `keywords`, `is_active`, `resource_type`, and nullable `program_name`, `target_population`, `eligibility`, and `referral_instruction`. A `people` row belongs to one service through `service_id` and supplies nullable contact fields. `resource_type` is `internal` or `external`. Preserve nulls and empty contact lists; do not fill gaps with generated details.

For this sprint, **source** in the frontend table means a service catalog record. The table shows all **active** internal and external services available to staff, with their source type; it does not expose inactive records. Use `service_id` as the stable key across the API, agent, and UI.

Keep three backend responsibilities distinct:

1. `ResourceRepository` reads service records and contacts by ID or as a bounded list, following `ChatRepository`'s constructor pattern. It does **not** implement text search.
2. A separate search data-access module runs the ranked Supabase search and returns ordered active service IDs and fields.
3. `ResourceAgent` receives these dependencies, builds the prompt, offers the search tool, and explains retrieved facts. The model never receives database credentials.

Owners can build against a fake repository or inline fictional rows before another task lands. The final integration should use one service schema and one shared Supabase client from `apps/api/app/main.py` and `apps/api/app/dependencies.py`.

## Integration order and sprint demo

The seven tasks are available in parallel, with fakes where needed. When merging, first settle the `services`/`people` schema and the search return shape. Then connect the resource and search providers to the agent, connect the catalog route to the table, and run the agent evaluation cases against the integrated code. Tasks 1, 2, and 4 may touch files from the October 24 sprint; Task 6 may touch files from October 31. Merge those edits with the existing implementations rather than replacing them.

The demo target is a fictional Supabase catalog that appears in the source table, can be searched by the chat agent, and can be opened for current recorded service details. A staff member should see a clear no-match answer and clear labels for missing eligibility or contact data. Refreshing a chat should preserve its conversation. The evaluation command should report which fictional scenarios pass or fail.
